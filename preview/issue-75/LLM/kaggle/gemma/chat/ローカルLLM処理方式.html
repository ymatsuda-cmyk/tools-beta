全体構成

クライアントは2種類、経路は2本。灰色が制御、緑がデータを運ぶ。 この2本が交わらないことが、この構成の設計上いちばん重要な性質。

経路の分離

Apps Script を制御に使い、チャットは通さない。これは好みではなく、 通さざるを得ない理由が3つある。

制約影響
リクエストは GET のクエリ文字列長文もファイルも載らない
レスポンスを分割送信できないストリーミング不可。無音で数十秒待つことになる
UrlFetchApp の上限は約60秒3万トークンの prefill に間に合わない

よってデータは ブラウザ → ngrok → プロキシ の直通、 制御だけが ブラウザ → Apps Script → Kaggle API を通る。 Kaggle の API キーが Apps Script の外に出ないという副次的な利点も、この分離から来ている。

起動から停止まで

Kaggle には「カーネルを停止する API」が存在しない。 そのため停止は、notebook 自身にポーリングさせて自ら終わらせる形をとっている。

チャット1往復

送信前に推定し、応答後に実測と突き合わせる。この二段構えが、 この基盤でいちばん厄介な失敗——無言の切り捨て——への対策になっている。

無言の切り捨て。 入力が num_ctx を超えると、Ollama はエラーを返さずに前半を捨て、 残った後半だけで応答する。それらしい答えが返るため気づけない。 実測では上限の半分ちょうどの位置で切られた。

プロキシが担っていること

Ollama にも /v1 はあるが、間に自前のプロキシを挟んでいる。 理由は Bearer 認証、CORS ヘッダ、思考モードの抑止、 そしてストリーミング時に usage を返すこと。 最後の1つは Ollama の /v1 が返してくれないため、 切り捨て検知のために自前で載せ替える必要があった。

設定と秘密情報

3つの秘密が登場する。性質が違うので、置き場所を混同しないこと。

値置き場所ブラウザに出るか守っている対象
KAGGLE_API_KEYApps Script のみ出さないKaggle アカウント全体
CONTROL_TOKENApps Script ＋ ブラウザ出るGPU の起動
PROXY_API_KEYApps Script ＋ ブラウザ出るGPU の利用

下2つはブラウザに入る前提の値で、アプリ利用者から隠す秘密ではない。 守っているのは「URL を偶然知った第三者が GPU 枠を消費すること」に限られる。 Kaggle の API キーだけは性質が違い、これはアカウント全体の操作権限を持つ。

notebook のソースはプロパティではなく、プロジェクト内の proxy_py.html に置いている。 プロパティは1件あたり 9KB までで、10KB を超えるソースは入らない。 Apps Script が push の直前にプレースホルダへ実際の値を差し込む。

実測値

この基盤の設定値は、ほぼすべて測って決めた。 ドキュメントに書くべきは「推奨値」ではなく「測った値と、測った条件」だと考えている。

prefill 速度 270 tok/s 実測 / 4条件

5,000〜50,000字の4条件で 263〜280 tok/s と一定。 待ち時間の予測式はこの値を使っている。生成側は別で約 20 tok/s。

コンテキスト長 32,768 VRAM 制約

モデル自体は 262,144 まで対応する。32,768 に抑えているのは P100 の 15.9GB が理由で、 モデルの制約ではない。KV キャッシュが収まるならまだ上げられる。

入力の実質上限 30,000 tok 導出

出力用に 2,048 を残した残り。日本語の散文なら約 7万字、 コードや ID が混じると約 3.7万字。字数ではなくトークン数が上限を決める。

トークン効率 0.50 tok/字 実測 / 回帰

5往復の会話から tokens ≒ 0.50 × 文字数 + 17。誤差は数トークン。 英数字の羅列は逆に 0.82 tok/字と重くなる。アプリは実測値で係数を自動較正する。

週次クォータ 30 時間 Kaggle 仕様

リセットは土曜の朝（UTC）。需要によって変動するため 30 は目安。 集計を月曜起点にしていた時期があり、残量を過大に見積もっていた。

設計判断の記録

OpenAI 互換に寄せた

Ollama 独自の /api/chat ではなく /v1/chat/completions を話す。 これ1本で Obsidian Copilot、VS Code、Python SDK、curl がすべて同じ設定で繋がる。 他のアプリから使うための API を「作る」必要がなく、すでにあることになる。

ビルドをやめた

React と Vite で組んだあと、素の JS / HTML / CSS に作り直した。 importmap で CDN から ESM を読めばモジュール分割は保てる。 npm install も GitHub Actions も不要になり、 Pages の base パスの罠も消えた。失ったのは型チェックと差分描画で、 後者は Markdown のスロットル描画で埋めている。

Apps Script との通信は JSONP

ウェブアプリの /exec はレスポンス時にリダイレクトが挟まり、 ブラウザからの fetch は環境によって CORS が不安定になる。 JSONP なら CORS の対象外で確実に通る。 代償として CONTROL_TOKEN が URL に載るため、 このトークンで守る対象は GPU の起動だけに留めている。

notebook のソースは Drive ではなくプロジェクト内に

当初は Drive の .ipynb を読んでいたが、 Apps Script 内の HTML ファイルに Python を直接置き、 ipynb の JSON は push 時に組み立てる形に変えた。 DriveApp のスコープが不要になり、 編集対象がエスケープ済み JSON から素の Python になった。

つまずいた記録

原因の特定に時間がかかったものを、症状と実際の原因の対で残しておく。 どれも「表示されるエラーが本当の原因を指していない」種類のもの。

  1. HTTP/2 の PROTOCOL_ERROR と 400 Bad Request プロキシの実装を疑ったが、原因は環境変数に入れた API キーに余計な文字が混ざっていたこと。 ヘッダとして送れない値だったため、ngrok のエッジに到達する前に捨てられていた。 でたらめな32桁を直接書いて 401 が返ることを確認したのが決め手。
  2. Google ドライブの「ファイルを開くことができません」 Apps Script のウェブアプリ URL を開いたときの症状。URL の形式ではなく、 そのデプロイ ID がもう有効でなかった。デプロイを作り直して解決。 コードを保存しただけではウェブアプリに反映されない点も同根。
  3. 入力欄で1文字打つとフォーカスが外れる 入力イベントで DOM を丸ごと作り直していたため、textarea が一度 DOM から外れていた。 構造の組み立てと値の更新を分離して解決。素の JS に移した際に持ち込んだ問題。
  4. 画像を添付してもモデルが認識しない プロキシの実装やモデルの対応状況を疑ったが、原因は Kaggle のデータセットに入れていた モデルの複製が不完全で、画像エンコーダのブロブが欠けていたこと。 Kaggle 上で公式から取り直してデータセットを作り直した。
  5. preflight が CORS で弾かれる Authorization ヘッダを付けると OPTIONS が先に飛ぶが、 そこには ngrok-skip-browser-warning が乗らない。 ただし多くの場合、実体は「Kaggle が停止していて ngrok がエラーページを返している」だけだった。 オフラインが CORS エラーの顔をして現れる。
  6. Kaggle のセルが謎の FileNotFoundError で落ちる ollama が無いというエラーだったが、実際の原因は40秒前の行にあった。 インターネットが無効で、あるいは zstd が無くてインストーラが失敗していた。 導入直後に成否を確認する行を入れて、原因の位置を前に持ってきた。
