# 提案ナレッジ（議事録→ROI試算→提案）

議事録の登録 → ROI試算 → 課題×解決案の提案 → 提案書用プロンプト出力、を行う仕組みです。
**2つのアドインで役割を分けています。**

| アドイン | 役割 |
|---|---|
| 営業報告（既存アドイン） | 簡単な操作のみ：議事録の紐づけ・参照、ROI提案の作成・参照 |
| 提案ナレッジ（本アドイン） | 詳細な操作：AI抽出結果の確認・修正、課題ごとの試算→解決策→投資効果のウィザード、提案書用プロンプトの組み立て |

Excelの操作とAI呼び出しのロジックは両アドインで共有する **`roi-core.js`** に一本化しています。営業報告アドイン側は `roi-core.js` と、簡易パネルの `eigyo-roi-panel.js` を読み込むだけで4操作が使えます。**既存の営業報告のシート・コードは一切変更しません**。同じワークブックに新しいシート（後述）を追加するだけです。

## 画面構成（提案ナレッジ、3タブ）

| タブ | 内容 |
|---|---|
| ①議事録入力 | 案件を選択（顧客名・案件名つき）し、**1案件に複数の議事録**をタイトル付きで登録。「課題を抽出」で議事録すべてから**複数の課題を一括抽出**する。既存の課題がある場合は差分を確認してから反映。下部に案件ごとの課題件数一覧を表示し、抽出済みの案件をタップすると②タブが開く |
| ②提案 | 課題を一覧表示（右に損失コスト/年）。クリックでアコーディオンが開き、課題内容と試算→解決策→投資効果の3ステップウィザードに入る。ステップ3で「提案に含める」と画面上部の全体回収に反映される |
| ③プロンプト出力 | 提案に含めた課題から、生成プロンプト・顧客インプット・ROI数値・章立て骨子（採用した解決策・改善率・根拠つき）をブロックごとにコピーできる形で出力 |

## ファイル構成

```
proposal/
├── manifest.xml          … 提案ナレッジアドイン本体のマニフェスト
├── index.html / app.js   … 提案ナレッジの詳細UI（3タブ）
├── roi-core.js           … 共有ライブラリ（Excel操作・AI呼び出し。DOM非依存）
├── eigyo-roi-panel.js    … 営業報告アドインに埋め込む簡易パネル（後述）

```

## 営業報告アドインへの組み込み方

営業報告アドイン（`eigyo/`）側の変更は最小限です。

1. `roi-core.js` と `eigyo-roi-panel.js` を、営業報告アドインと同じ `tools/addin/` 直下の兄弟フォルダ `proposal/` に配置する（このリポジトリの実際の構成）。営業報告の `index.html` の `<head>` には、絶対URLではなく**相対パス**で追加する（`eigyo/` と `proposal/` が兄弟フォルダのため）。

   ```html
   <script src="../proposal/roi-core.js"></script>
   <script src="../proposal/eigyo-roi-panel.js"></script>
   ```

2. 編集画面（ステージタブ式モーダル）のHTMLに、マウント先を1つ追加する（備考欄の近くなど、どのステージでも見える位置を推奨）。

   ```html
   <div id="roi-panel-mount"></div>
   ```

3. モーダルを開く処理・表示中の案件が切り替わる処理の中で、以下を呼ぶ。

   ```js
   RoiPanel.mount(document.getElementById("roi-panel-mount"), rec.id, {
     getMemo: () => document.getElementById("ed-remarks").value, // 既存の備考欄などを渡すと精度が上がる
   });
   // getMemo を省略した場合はパネル内に簡易メモ欄が自動で表示される
   ```

これだけで、編集画面に「議事録・提案」というアコーディオンパネルが表示されます。営業報告アドイン側のコードは、この1行を呼ぶだけで済み、Excel操作やAI呼び出しの中身には一切触れません。

### 営業報告側の操作（`eigyo-roi-panel.js`、アコーディオンUI）

- **「提案」ボタン（ti-list アイコン）**：作成済みの課題をアコーディオンで一覧表示。各行クリックで詳細（ROI内訳・解決策・元データリンク）を展開
- **「作成」アイコン（ti-sparkles）**：この案件に紐づく議事録すべて＋メモを1回のAI呼び出しで判定し、該当する課題カテゴリをまとめて一覧に追加する。カテゴリの事前選択は不要（AIがどのカテゴリが当てはまるか自体を判定する）
- **チェックボックス**：提案書に含める課題を複数選択（チェックした瞬間にROI試算シートの「選択」列へ保存）
- **「提案書を作成」ボタン**：選択済みの課題について、元になった議事録（参照URLまたはテキスト）のリンク一覧を表示する。実際のプロンプト組み立て・提案書生成は提案ナレッジ側で行う（このボタンは元データの所在を一覧化するだけ）

議事録の紐づけ自体（テキスト貼り付け／参照URL登録）は、別途PLAUD/Notion同期などの既存フローで `議事録` シートに書き込まれる想定。営業報告アドイン側にその場で1件だけ手打ちしたい場合のために、メモ欄（`getMemo` を渡さない場合に表示される簡易テキストエリア）も用意している。

## 追加されるシート（既存シートは無改変）

### ROIマスタ

課題カテゴリ・項目ID・項目名・区分（入力/出力）・単位・デフォルト値・**数式（項目IDのトークン式、例: `stk_people*stk_hours*stk_freq`）**・信頼度初期値・**利用範囲**・**作成案件ID**。

利用範囲は `共通`（全案件で使う正式カテゴリ）と `一時`（作成した案件でのみ使う）の2種類。AIとの壁打ちで作った新カテゴリは、既定では `一時` として登録され、他案件のカテゴリ一覧には出てこない。これにより、案件ごとにAIが少しずつ違う名前のカテゴリを作ってマスタが増殖するのを防ぐ。

同じカテゴリが複数案件で使われるようになったら、`promoteTempCategory()` で利用範囲を `共通` に変えるだけで正式カテゴリに昇格できる（行の作り直しは不要）。`listTempCategories()` は一時カテゴリと、それが実際に何案件で使われているかを返すので、マスタ化の判断材料になる。初回起動時に9カテゴリ（在庫管理・ロット管理・AI議事録・製造管理・OCR受注入力・Delphi移行・属人化・情報共有・問合せ対応）をサンプル投入する。うち6カテゴリはROI試算式を持ち、残り3カテゴリ（属人化・情報共有・問合せ対応）は数値化が難しい課題として、カテゴリ一覧に出すための最小限の入力項目だけを持つ（削減額は「—」表示になり、解決案は定性情報のみで判断する）。

### 議事録

案件ID・**タイトル**・参照URL・発言テキスト・登録日時・**議事録ID**。1案件に複数の議事録を登録でき、タイトル（「初回訪問ヒアリング」など）で区別する。参照URLは、PLAUD/Notionなど既存の議事録ビューアに保管されているテキストへのリンクだけを持たせたい場合に使う（発言テキスト欄は空でもよい）。議事録IDは、ROI試算シート側から「どの議事録が根拠か」を辿るための一意キー（自動採番）。

### ROI試算

案件ID・課題カテゴリ・項目ID・項目名・区分・値・単位・信頼度・選択（提案書に含めるかのチェック）・更新日時・**根拠議事録ID**（カンマ区切り）。出力行の「値」はExcelの数式（`INDEX`/`MATCH`）で、同じ案件内の入力行を参照して自動計算される。計算ロジックはJS・AIのどちらにも持たせていない。

根拠議事録IDは、そのカテゴリを作成した時点でこの案件に紐づいていた議事録IDをまとめて記録する簡易実装（カテゴリ単位で「どの発言が根拠か」までは追跡しない）。営業報告側の「提案を見る」「提案書を作成」は、ここから議事録の参照URL・テキストを引いて一覧表示する。

### ソリューションDB

課題カテゴリ・解決策名・コスト感（低／中／高）・実現方法・**概算導入費**・**改善率**・**削減根拠**・**根拠区分**。**1つの課題カテゴリに複数行を持たせ、低コスト〜高コストの解決案を並べて提示する**設計。

改善率は削減額を決める最も影響の大きい数値なので、根拠をセットで持たせている。

| 根拠区分 | 意味 | 信頼度の重み |
|---|---|---|
| 実績 | 自社の導入事例があり、具体的な数字が示せる | 1.0 |
| 推定 | 類似案件から見積もった | 0.5 |
| 一般値 | 自社実績がなく業界一般値を採用（提案時は幅を持たせて説明する） | 0.25 |

概算導入費・改善率・削減根拠・根拠区分はあくまで**初期値**で、案件ごとに提案ナレッジの②タブで書き換えられる。書き換えた内容はマスタではなく後述の「提案決定」シートに保存されるため、マスタは汚れない。

### 抽出課題

**カテゴリに当てはまるかに関わらず、顧客が語った課題はすべて記録する。** カテゴリ整備が追いついていないという自社都合で、顧客の課題を取りこぼさないため。

### 粒度と種別

抽出時、AIには次の2つを守らせている。

**粒度**: 個別の事象を1件ずつ並べず、「その課題で提案書を1本書けるか」を目安に提案の単位でまとめる。同じ原因・同じ業務から生じている事象は1つに集約し、出力は最大5件まで。まとめる前の個別事象は `根拠事象` 列に残るので、商談中に「具体的には」と聞かれたら展開できる。

**種別**（`種別` 列）:

| 種別 | 扱い |
|---|---|
| 経営課題 | 提案・ROI試算の対象。②タブの一覧に出る |
| 改修要望 | 既存案件への不具合報告・改善要望。②タブでは別枠に分けて表示し、既存の `課題` シートへ転記する想定 |
| 対象外 | 打合せ中の一時的な事象など。表示しない |

議事録が既存案件の進捗確認会議だった場合、改修要望ばかりになるのは正常な動作。AIには「経営課題を無理に作り出さない」よう指示している。

案件ID・課題ID・課題カテゴリ・課題タイトル・課題内容・AI原文タイトル・AI原文内容・**割当状態**・**AI候補**・根拠議事録ID・抽出日時。課題IDで一意に識別し、1案件に同じカテゴリの課題が複数あってもよい。

| 割当状態 | 意味 |
|---|---|
| 未設定 | AIがカテゴリを判定できなかった。担当者が候補から選ぶ |
| 割当済 | カテゴリが決まり、ROI試算の対象 |
| カテゴリなしで提案 | 金額は出さないが、課題として提案書に載せる |
| 対象外 | 一覧には残すが提案には含めない |

AI候補列には、AIが提示したカテゴリ候補（名前・既存か新規か・理由）がJSON形式で入る。担当者はこの候補から選ぶか、AIと相談して新しいカテゴリを設計する。


案件ID・課題カテゴリ・課題タイトル・課題内容・**AI原文タイトル**・**AI原文内容**・根拠議事録ID・抽出日時。AIが議事録から抽出した課題を保持する。**1つの議事録から複数の課題が抽出されるのが前提**で、案件ID×課題カテゴリで1行。同じ組み合わせの行は再抽出時に上書きされる。

課題タイトルはカテゴリ名の再掲ではなく、その顧客固有の状況を一行で表したもの（例「棚卸と在庫差異の調査に時間がかかっている」）。課題内容は現状の進め方・困りごと・その影響を2〜3文で記述したもので、②タブのアコーディオンを開いたときに表示される。

数値が読み取れなかった課題（属人化など金額換算しにくいもの）も、議事録で困りごととして語られていればこのシートに残る。②タブでは損失が「未算出」と表示され、解決案のみ提示される。

既存ワークブックの `課題` シート（課題管理表）とは別物なので、名前を分けている。

### 再抽出したときの上書き

議事録を追加して再抽出すると、既存の課題と突き合わせて差分を表示し、反映するかを確認する。判定は「AI原文」列との比較で行う。

| 状態 | 判定 | 既定の動作 |
|---|---|---|
| 新規 | 既存の行がない | 確認なしで追加 |
| 未編集 | 課題タイトル・内容がAI原文と一致 | 確認なしで自動更新 |
| 編集済み | 営業が手を入れてAI原文と異なる | **現在の内容を残す**（画面で上書きを選べる） |

全件に確認を出すと毎回「全部OK」を押すだけになるため、編集済みの課題だけを確認対象にしている。またROI数値（棚卸人数など）は選択に関わらず更新する。文章には営業の判断が入りうるが、数値は新しい議事録のほうが正確なはずのため、両者を分けている。

「残す」を選んだ場合も、AI原文の列は最新の抽出結果で更新される。次回の編集判定が最新のAI出力を基準に行われるようにするため。

### 提案決定

案件ID・課題カテゴリ・解決策名・導入費・改善率・削減根拠・根拠区分・提案に含める・更新日時。②タブのステップ3で「提案に含める」を押したときに、その案件で選んだ解決策と書き換えた数値を保存する。同じ案件・同じ課題カテゴリの行は上書きされる。

### 信頼度の考え方

信頼度は2つの要素を1:1で合成している。

1. **入力値の確からしさ** — ROI試算シートの各入力行の信頼度（確定1.0／推定0.5／未確認0）の平均
2. **改善率の根拠** — 採用した解決策の根拠区分（実績1.0／推定0.5／一般値0.25）

入力値がすべて確定でも、改善率が一般値なら信頼度は上がりきらない。これは意図的で、試算結果への影響が大きいのは改善率のほうであるため。②タブでは課題ごとの信頼度と、画面上部に「損失合計の信頼度」「全体回収の信頼度」を表示する。全体回収の信頼度は、提案に含めると決定した課題だけから算出する（未検討の課題の不確かさが、決めた提案の確からしさを引きずり下げないようにするため）。

## AI連携（ブラウザから直接呼び出し。GASは廃止）

**社内利用限定という前提で、GASを介さずブラウザから直接AI APIを呼ぶ構成にしている。** 議事録の内容や案件情報を扱うため、この構成には明確なリスクがある。

- APIキーは `localStorage` に保存され、開発者ツール（Networkタブ）から見える
- `roi-core.js` 自体もGitHub Pagesで公開されており、URLを知っていれば誰でもソースを読める
- アドインのURLと使い方を知っている人は誰でも、このAPIキーでAnthropic（または設定したプロバイダ）への課金・利用枠を消費できる

**社外に公開しないこと。** 外部提供や、社内でも利用者を限定できない状況になった場合は、APIキーをサーバ側にのみ置く構成（GAS等）に戻すことを検討する。

### 設定（⚙）に入力する項目

| 項目 | 内容 |
|---|---|
| プロバイダ | `Anthropic（Claude）`（既定）または `OpenAI互換（Gemini等）` |
| ベースURL | Anthropicは未入力で既定値（`https://api.anthropic.com/v1/messages`）を使う。OpenAI互換は必須（例: Geminiなら `https://generativelanguage.googleapis.com/v1beta/openai`。`/chat/completions` は自動で付加する） |
| APIキー | 契約しているプロバイダのAPIキー |
| モデル | 未入力ならAnthropicは `claude-sonnet-4-6`、OpenAI互換は `gpt-4o-mini` |

営業報告アドインと`localStorage`を共有するため、提案ナレッジ側で一度設定すれば営業報告アドインの「作成」アイコンからも同じ設定が使われる。

### Anthropicを直接呼ぶ場合の注意

Anthropic APIはブラウザからの直接アクセスを既定でブロックしている。`roi-core.js`はこれを許可するため、リクエストヘッダーに `anthropic-dangerous-direct-browser-access: true` を付けている（`callAiModel()` 内）。ヘッダー名の通り「危険」を明示するためのものであり、上記のキー露出リスクを軽減するものではない。

### 参照URLの取得について

議事録の「参照URL」機能（PLAUD/Notion等へのリンクだけを登録するケース）は、以前はGAS（サーバ側）が`UrlFetchApp`でページ内容を取得していたが、直接呼び出しに変更したことでbrowser側の`fetch()`に置き換わっている。**多くのサービスはブラウザからのクロスオリジン取得を許可していないため、参照URLからの本文取得は失敗することが多い。** 失敗した場合はそのURLをスキップし、consoleに警告を出す（`[RoiCore] 参照URLの取得に失敗しました`）。確実に使いたい場合は、テキストを直接貼り付ける運用にする。

## デプロイ手順（GitHub Pages）

**`roi-core.js` や `app.js` を更新したら、`index.html` の `<script src="...?v=YYYYMMDDx">` のバージョン文字列を毎回変える。** ブラウザ・GitHub Pages側のキャッシュにより、バージョンを変えないと更新が反映されないことがある（実際に、抽出処理を何度も直したのに古いコードが動き続ける不具合が発生したため）。営業報告アドイン側の `eigyo-integrated/index.html` にある相対パス参照（`../proposal/roi-core.js?v=...`）も同様。

1. `manifest.xml` `index.html` `app.js` `roi-core.js` `style.css` `commands.html` `commands.js` `icons/` 一式を、営業報告アドインと同じリポジトリの `tools/addin/proposal/` に配置
2. `icons/` は暫定的に営業報告アドインのアイコンを流用。実運用前に差し替える
3. `manifest.xml` をサイドロード、または管理センターから組織展開
4. Excelで対象ブックを開き、ホームタブの「提案ナレッジ」ボタンでタスクペインを表示

## デモモード

`index.html` をブラウザで直接開くと、Excelに接続せずデモバッジ表示で起動する（書き込み系の操作はシミュレーションのみ）。

## 既知の制約・今後の調整ポイント

- ①の「保存」は、対象カテゴリの行がまだ無ければ追加する方式。ROIマスタの数式を後から変更しても、既存の出力行の数式は自動更新されない（該当行を削除してから再度反映する）。
- ②の「削減額」表示は、項目IDが `_saving` で終わる出力項目を主要指標として自動採用している。カテゴリごとに主要指標が複数ある場合は判定ロジック（`getProposalSummaryForCase`）を調整する。
- 数式は `INDEX`/`MATCH` の動的配列前提（モダンExcel想定）。
- 議事録本文（貼り付けテキスト）は1件あたり30,000文字を超える分を自動的に切り詰めてから送信する（`capText()`）。当初は6,000文字で切っていたが、音声認識の誤変換によるノイズの羅列が冒頭に来る議事録では、実質的な内容が切り捨てられて課題が0件抽出される事故が起きたため引き上げた。長い文字起こしをまるごと貼り付けた場合、冒頭の雑談やノイズが長いと後半の実質的な内容がそれでも切り捨てられる可能性がある点に注意。気になる場合は、要点だけを先頭にまとめてから貼り付けるとよい。
- 案件IDの比較は前後の空白を無視する（`sameId()`）。営業報告シート等からのコピー&ペーストで末尾スペースが混入しても、議事録・ROI試算・抽出課題・提案決定の紐づけが外れないようにするため。全角スペースの混入までは吸収しない（半角トリムのみ）。
- 根拠議事録IDは「そのカテゴリを作成した時点で案件に紐づいていた議事録すべて」を記録する簡易実装。発言単位でどれが根拠かまで厳密に追跡したい場合は、`autoExtractProposals` のAI応答に `usedHearingIds` を持たせるようGASプロンプトを拡張する必要がある。
- 「提案書を作成」ボタンは元データリンクの一覧化までで、実際のプロンプト組み立て・pptx化は提案ナレッジ側の③タブで行う設計。
